# Проектирование базы данных видеохостинга

Необходимо спроектировать реляционную базу данных для сервиса, похожего на YouTube.

Сервис позволяет людям создавать каналы, публиковать видео, смотреть материалы других авторов и взаимодействовать с ними. Ваша задача — самостоятельно определить, какие таблицы, поля, первичные и внешние ключи нужны такой системе.

Писать программу и создавать базу данных на компьютере не требуется. Результатом работы должна стать понятная схема базы данных на бумаге.

## Что должна уметь хранить система

В базе должна сохраняться информация, необходимая для следующих возможностей.

### Пользователи и каналы

- Пользователь регистрируется в сервисе.
- Для пользователя сохраняются данные, необходимые для входа и отображения профиля.
- Один пользователь может создать несколько каналов.
- У каждого канала есть владелец, название, уникальный адрес, описание и дата создания.
- Пользователь может подписываться на чужие каналы и отменять подписку.
- Для подписки нужно знать, кто подписался, на какой канал и когда это произошло.

### Видео

- Канал может публиковать несколько видео.
- Для видео сохраняются название, описание, продолжительность, адрес файла или идентификатор хранилища, дата публикации и состояние доступности.
- Видео может быть открытым или закрытым.
- Видео относится к одной основной категории.
- Одному видео можно назначить несколько тегов.
- Один и тот же тег может использоваться у разных видео.

### Просмотры

- Система должна сохранять историю просмотров каждого пользователя.
- Нужно знать, кто посмотрел видео, какое видео было открыто и когда это произошло.
- Один пользователь может открыть одно видео несколько раз. Каждый такой просмотр должен сохраняться как отдельное событие.
- Общее количество просмотров должно получаться из истории, а не вручную дублироваться в нескольких местах.

### Реакции

- Пользователь может поставить видео положительную или отрицательную реакцию.
- На одном видео у пользователя может быть не более одной текущей реакции.
- Пользователь может изменить реакцию или удалить её.
- Количество положительных и отрицательных реакций должно вычисляться из сохранённых действий.

### Комментарии

- Пользователь может оставить комментарий под видео.
- Комментарий принадлежит конкретному автору и конкретному видео.
- Для комментария сохраняются текст, дата создания и, при необходимости, дата редактирования.
- Пользователь может ответить на другой комментарий.
- Для ответа нужно понимать, к какому комментарию он относится.
- Комментарии также могут получать реакции пользователей.

### Плейлисты

- Пользователь может создавать собственные плейлисты.
- У плейлиста есть название, описание и режим видимости.
- В один плейлист можно добавить несколько видео.
- Одно видео может находиться в разных плейлистах.
- Для видео внутри плейлиста нужно сохранять порядок.
- Также нужно знать дату добавления видео в плейлист.

### Жалобы

- Пользователь может отправить жалобу на видео или комментарий.
- Для жалобы сохраняются автор, причина, пояснение, дата создания и состояние рассмотрения.
- Жалоба должна однозначно указывать на объект, на который она была отправлена.

### Уведомления

- Сервис может создавать уведомления для пользователя.
- Уведомление содержит текст, дату создания и ссылку на нужный раздел сервиса.
- Система должна понимать, прочитано уведомление или нет.

## Основные бизнес-правила

При проектировании учитывайте следующие ограничения:

- адрес электронной почты пользователя не должен повторяться;
- адрес канала должен быть уникальным;
- название категории не должно повторяться;
- название тега не должно повторяться;
- одна и та же подписка не должна создаваться несколько раз;
- у пользователя может быть только одна текущая реакция на конкретное видео;
- одно видео не должно несколько раз занимать одну позицию в одном плейлисте;
- отрицательная продолжительность видео недопустима;
- дата редактирования не может использоваться вместо даты создания;
- пароль нельзя хранить в открытом виде.

## Что такое проектирование базы данных

Проектирование базы данных начинается не с рисования случайных таблиц. Сначала нужно понять предметную область и правила системы.

Работу удобно выполнять в следующем порядке.

### 1. Найдите сущности

Сущность — самостоятельный объект предметной области, информацию о котором нужно хранить.

Чтобы найти сущности, выпишите существительные из описания сервиса. Затем решите, какие из них являются самостоятельными объектами, а какие — просто свойствами или действиями.

Не каждое слово должно превращаться в отдельную таблицу. И наоборот, не нужно пытаться сохранить всю систему в одной огромной таблице.

### 2. Определите свойства

Для каждой найденной сущности определите необходимые свойства.

У каждого поля должны быть:

- понятное название;
- подходящий тип данных;
- отметка, обязательно ли значение;
- ограничение уникальности, если повторение недопустимо.

Не следует сохранять данные «на всякий случай». Каждое поле должно иметь понятное назначение.

### 3. Выберите первичные ключи

Первичный ключ, или `PRIMARY KEY`, однозначно определяет запись.

Требования к первичному ключу:

- значение не повторяется;
- значение не может отсутствовать;
- по ключу можно найти ровно одну запись;
- ключ не должен постоянно меняться.

В качестве ключа часто используют отдельный числовой идентификатор. В таблице-связке первичный ключ может состоять из нескольких внешних ключей.

### 4. Определите связи

Для каждой пары связанных сущностей определите тип связи.

#### Один к одному — 1:1

Одной записи первой сущности соответствует не более одной записи второй.

#### Один ко многим — 1:N

Одной записи первой сущности соответствует несколько записей второй, но каждая запись второй относится только к одной записи первой.

#### Многие ко многим — M:N

Несколько записей первой сущности могут быть связаны с несколькими записями второй.

В реляционной базе связь M:N напрямую не хранится. Для неё создаётся промежуточная сущность, содержащая внешние ключи обеих сторон. У такой связи могут быть собственные свойства, например дата или позиция.

### 5. Расставьте внешние ключи

Внешний ключ, или `FOREIGN KEY`, ссылается на первичный ключ другой таблицы.

Он нужен, чтобы база не позволяла создать ссылку на несуществующий объект.

Для каждой связи нужно показать:

- где находится внешний ключ;
- на какой первичный ключ он ссылается;
- обязательна ли связь.

### 6. Уберите повторения

Если одно и то же значение приходится переписывать во множество строк, возможно, оно хранится не в том месте.

Повторение приводит к проблемам:

- одно значение исправили, а другое забыли;
- данные начинают противоречить друг другу;
- увеличивается размер базы;
- удаление одной строки может случайно удалить единственную важную информацию.

### 7. Проверьте вычисляемые значения

Не все значения нужно хранить отдельными полями.

Количество связанных записей, сумма, среднее значение и другие результаты часто можно вычислить запросом. Если хранить одновременно исходные события и их количество, данные могут разойтись.

Если вы всё же решили сохранить вычисляемое значение, необходимо объяснить, как система будет постоянно поддерживать его правильность.

## Нормализация

Нормализация — это способ организовать таблицы так, чтобы уменьшить дублирование и избежать противоречий при добавлении, изменении и удалении данных.

В этой работе база должна быть приведена как минимум к третьей нормальной форме — 3НФ.

## Первая нормальная форма — 1НФ

Таблица находится в 1НФ, если:

- каждая строка может быть однозначно определена;
- в каждой ячейке находится одно значение;
- в одном столбце хранятся значения одного смысла;
- отсутствуют повторяющиеся группы столбцов.

Плохо:

```text
интересы = "музыка, игры, программирование"
```

В одной ячейке находятся сразу три отдельных значения. По ним сложно искать, сортировать и создавать связи.

Также плохо:

```text
объект_1, объект_2, объект_3
```

Количество объектов заранее ограничено количеством столбцов. Добавление четвёртого объекта потребует изменения структуры таблицы.

Правильный подход — хранить отдельные значения в отдельных строках и связывать их ключами.

## Вторая нормальная форма — 2НФ

Таблица находится во 2НФ, если:

- она уже находится в 1НФ;
- каждый неключевой столбец зависит от всего первичного ключа.

Это особенно важно для таблиц с составным первичным ключом.

Представим связь с ключом `(object_a_id, object_b_id)`. Если дополнительное поле зависит только от `object_a_id`, оно описывает первый объект, а не саму связь. Такое поле нужно перенести туда, где хранится информация о первом объекте.

Свойства промежуточной сущности должны описывать именно конкретную связь двух записей.

## Третья нормальная форма — 3НФ

Таблица находится в 3НФ, если:

- она уже находится во 2НФ;
- каждый неключевой столбец зависит только от первичного ключа;
- неключевые столбцы не определяют другие неключевые столбцы.

Короткое правило:

```text
Каждое обычное поле должно описывать объект,
определяемый первичным ключом этой строки.
```

Пример нарушения 3НФ:

```text
content_id
content_title
author_id
author_name
author_email
```

`author_name` и `author_email` зависят от `author_id`, а не от самого `content_id`. Если имя автора хранится во многих строках, при изменении придётся обновлять каждую из них.

Для соблюдения 3НФ сведения об авторе должны храниться в сущности автора, а другая сущность должна содержать только ссылку на него.

## Как проверить 3НФ

Для каждой таблицы задайте три проверки:

1. Что именно описывает одна строка этой таблицы?
2. Все ли обычные поля описывают именно эту строку целиком?
3. Нет ли поля, которое на самом деле описывает другую сущность или определяется другим обычным полем?

Если на второй или третий вопрос нельзя уверенно ответить, структуру нужно пересмотреть.

3НФ не означает, что в разных таблицах вообще не могут встречаться одинаковые значения. Внешний ключ специально повторяется, чтобы связывать записи. Проблемой является бессмысленное копирование описательных данных.

## Правила именования

Во всей базе используйте один стиль. Одинаковые правила помогают понять схему без дополнительных пояснений.

### Используйте английский язык

Названия таблиц и полей записывайте английскими словами.

```text
Правильно:   users, created_at
Неправильно: пользователи, дата_создания
```

Не смешивайте русский и английский языки внутри одной схемы.

### Используйте snake_case

Все буквы должны быть строчными. Несколько слов разделяются символом подчёркивания `_`.

```text
Правильно:   user_profiles, created_at, category_id
Неправильно: UserProfiles, userProfiles, user-profiles, user profiles
```

Пробелы, дефисы и заглавные буквы в названиях не используйте.

### Называйте таблицы во множественном числе

Название таблицы показывает, что в ней хранится множество записей.

```text
Правильно:   users, categories, purchase_orders
Неправильно: user, category, purchase_order
```

Для промежуточной таблицы объедините названия связанных объектов так, чтобы название оставалось понятным:

```text
student_courses
user_roles
```

### Называйте поля понятно и кратко

Название поля обычно записывается в единственном числе:

```text
title
description
email
duration_seconds
```

Из названия должно быть понятно, что хранится в поле. Не используйте непонятные сокращения вроде `usr`, `cat`, `dt` или названия без смысла вроде `value1`.

### Первичный ключ называйте id

Основной числовой идентификатор таблицы называйте `id`:

```text
id BIGINT PK, AI
```

Не нужно повторять название таблицы в её собственном первичном ключе:

```text
Правильно:   id
Неправильно: user_id внутри таблицы users в роли её PK
```

### Внешний ключ заканчивайте на _id

Название внешнего ключа должно показывать, на какую сущность он ссылается:

```text
user_id      FK → users.id
category_id  FK → categories.id
```

Если у одной таблицы две разные связи с одной сущностью, укажите роль каждой ссылки:

```text
sender_user_id
receiver_user_id
```

### Логические поля начинайте с is_ или has_

Для значений `true` или `false` используйте названия, которые можно прочитать как вопрос:

```text
is_active
is_blocked
has_access
```

### Дату и время заканчивайте на _at

Момент события называйте с окончанием `_at`:

```text
created_at
updated_at
published_at
```

Если хранится только календарная дата без времени, используйте `_date`:

```text
birth_date
release_date
```

### Не используйте зарезервированные слова

Не называйте таблицы и поля словами, которые имеют специальное значение в SQL, например `order`, `group` или `table`. Выберите более точное название:

```text
purchase_orders
study_groups
users
```

## Как оформить результат

Работа выполняется в обычной тетради. Рисовать все таблицы на одном листе и соединять их длинными пересекающимися линиями не нужно. Удобнее записать каждую таблицу отдельным компактным блоком, а связи перечислить отдельно.

### Для каждой таблицы укажите

- выбранное вами название;
- список полей;
- тип каждого поля;
- первичный ключ `PK`;
- внешние ключи `FK`;
- уникальные поля `UQ`;
- обязательные и необязательные поля;
- краткое назначение таблицы.

Пример оформления без привязки к заданию:

```text
1. ENTITY_NAME — краткое назначение

id           BIGINT        PK, AI
title        VARCHAR(200)  NN
related_id   BIGINT        FK → OTHER_ENTITY.id, NN
description  TEXT          NULL
status       VARCHAR(20)   NN, DEFAULT 'active'
created_at   DATETIME      NN
```

Такой блок показывает название таблицы, её назначение, поля, типы данных и ограничения.

## Обозначения полей

| Обозначение | Полное название | Что означает |
| --- | --- | --- |
| `PK` | Primary Key | Первичный ключ, однозначно определяющий строку |
| `FK` | Foreign Key | Внешний ключ, ссылающийся на ключ другой таблицы |
| `UQ` | Unique | Значение не должно повторяться |
| `NN` | Not Null | Значение обязательно для заполнения |
| `NULL` | Nullable | Значение можно не указывать |
| `AI` | Auto Increment | Числовое значение автоматически увеличивается |
| `DEFAULT` | Default Value | Значение, которое используется, если другое не указано |
| `CHECK` | Check Constraint | Условие, которому должно соответствовать значение |

Одно поле может иметь несколько обозначений:

```text
id       BIGINT        PK, AI
email    VARCHAR(255)  NN, UQ
amount   DECIMAL(10,2) NN, CHECK >= 0
```

### Первичный ключ — PK

Первичный ключ не повторяется и не может быть пустым. В таблице может быть только один первичный ключ, но он может включать несколько полей.

Простой первичный ключ:

```text
id BIGINT PK, AI
```

Составной первичный ключ:

```text
PRIMARY KEY (first_id, second_id)
```

Составной ключ часто используется в промежуточной таблице и не позволяет дважды сохранить одну и ту же пару.

### Внешний ключ — FK

Внешний ключ показывает, с какой записью другой таблицы связана текущая строка.

Записывайте не только `FK`, но и цель ссылки:

```text
related_id BIGINT FK → OTHER_ENTITY.id
```

Тип внешнего ключа должен совпадать с типом поля, на которое он ссылается.

Если внешний ключ имеет `NN`, связь обязательна. Если разрешён `NULL`, связанная запись может отсутствовать.

### Уникальность — UQ

`UQ` используется, если две записи не могут иметь одинаковое значение:

```text
code VARCHAR(100) NN, UQ
```

Уникальной может быть комбинация нескольких полей:

```text
UNIQUE (first_id, second_id)
```

Такое ограничение запрещает повторение пары, но позволяет отдельно повторять каждое из двух значений.

### Обязательные и необязательные поля

`NN` означает, что поле нельзя оставить пустым:

```text
title VARCHAR(200) NN
```

`NULL` означает, что значение может отсутствовать:

```text
description TEXT NULL
```

Пустая строка и `NULL` — не одно и то же. Пустая строка является известным текстовым значением без символов. `NULL` означает, что значение отсутствует или неизвестно.

## Основные типы данных

| Тип | Какие значения хранит | Пример использования |
| --- | --- | --- |
| `INT` | Целые числа | Количество или продолжительность |
| `BIGINT` | Большие целые числа | Идентификатор записи |
| `VARCHAR(n)` | Короткий текст ограниченной длины | Название, адрес или код |
| `TEXT` | Длинный текст | Описание или комментарий |
| `BOOLEAN` | Истина или ложь | Включена ли настройка |
| `DATE` | Только дата | День рождения |
| `DATETIME` | Дата и время | Момент создания события |
| `DECIMAL(p,s)` | Точное дробное число | Цена или денежная сумма |
| `ENUM` | Одно значение из заранее заданного списка | Состояние или тип записи |

Число внутри `VARCHAR(n)` задаёт максимальную длину текста. Не используйте `VARCHAR` для любого значения только потому, что в него можно записать почти всё.

Для денежных значений обычно используют `DECIMAL`, а не `FLOAT`, чтобы избежать ошибок приближённого хранения.

В одной ячейке нельзя хранить список значений через запятую. Для повторяющихся и связанных значений нужны отдельные строки и связи.

### ENUM: выбор из готового списка

`ENUM` используется, когда поле может принимать только одно значение из небольшого заранее известного списка.

Например, видео может быть открытым или закрытым:

```sql
visibility ENUM('public', 'private') NOT NULL DEFAULT 'public'
```

Допустимые значения:

```text
'public'
'private'
```

Записать в такое поле другое значение нельзя. Например, значение `'unknown'` не входит в список.

`ENUM` удобно использовать для небольшого набора состояний, который редко меняется. Если варианты должны часто добавляться и редактироваться, для них лучше выделить отдельную связанную таблицу.

## Какие связи бывают

### Один к одному — 1:1

Одной записи первой таблицы соответствует не более одной записи второй таблицы.

```text
TABLE_A  1 ─── 1  TABLE_B
```

Для такой связи внешний ключ обычно имеет ограничение `UNIQUE`.

### Один ко многим — 1:N

Одной записи первой таблицы может соответствовать много записей второй. Каждая запись второй таблицы относится только к одной записи первой.

```text
TABLE_A  1 ─── N  TABLE_B
```

Внешний ключ находится на стороне `N`:

```text
TABLE_A.id  1 → N  TABLE_B.table_a_id
```

### Многие ко многим — M:N

Много записей первой таблицы связано со многими записями второй.

```text
TABLE_A  M ─── N  TABLE_B
```

Такая связь создаётся через промежуточную таблицу:

```text
TABLE_A  1 ─── N  TABLE_A_B  N ─── 1  TABLE_B
```

Промежуточная таблица содержит внешние ключи обеих сторон. В ней также хранятся свойства самой связи: дата создания, состояние, порядок и другие значения.

### Связь таблицы с самой собой

Иногда запись может ссылаться на другую запись этой же таблицы:

```text
parent_id BIGINT FK → THIS_TABLE.id, NULL
```

Так можно хранить иерархию, дерево или ответы на другие записи.

## Обязательность связи

Тип связи можно записывать точнее:

| Обозначение | Значение |
| --- | --- |
| `0..1` | Связанной записи может не быть или может быть одна |
| `1` | Должна быть ровно одна связанная запись |
| `0..N` | Может не быть ни одной или может быть несколько |
| `1..N` | Должна быть хотя бы одна, но может быть несколько |

Пример:

```text
TABLE_A  1 ─── 0..N  TABLE_B
```

Одна запись `TABLE_A` может не иметь связанных строк `TABLE_B` или иметь несколько. Каждая строка `TABLE_B` обязательно относится к одной строке `TABLE_A`.

## Как записывать связи в тетради

После блоков таблиц перечислите связи отдельными строками:

```text
СВЯЗИ

TABLE_A.id  1 → N  TABLE_B.table_a_id
TABLE_C.id  1 → 0..N  TABLE_D.table_c_id
```

Для связи M:N покажите промежуточную таблицу и обе связи 1:N:

```text
TABLE_A.id  1 → N  TABLE_A_B.table_a_id
TABLE_B.id  1 → N  TABLE_A_B.table_b_id
```

## Что должно быть в готовой работе

- все самостоятельно выделенные таблицы;
- назначение каждой таблицы;
- поля и типы данных;
- отметки `PK`, `FK`, `UQ`, `NN`, `NULL`, `AI`, `DEFAULT` и `CHECK`, где они необходимы;
- отдельный список связей `1:1`, `1:N` и `M:N`;
- цели всех внешних ключей;
- обязательность связей;
- промежуточные таблицы для связей M:N;
- какие значения должны быть уникальными;
- какие значения можно не заполнять;
- какие данные вычисляются, а не хранятся;
- как предотвращаются повторные реакции и подписки.

## Требования к работе

- База должна поддерживать все возможности из описания.
- Структура должна быть реляционной.
- Каждая таблица должна иметь первичный ключ.
- Все связи должны быть показаны внешними ключами.
- Связи M:N должны быть правильно разрешены.
- Таблицы и поля должны называться на английском языке в стиле `snake_case`.
- Названия таблиц должны быть во множественном числе.
- Имена не должны содержать пробелы, дефисы и непонятные сокращения.
- Первичный ключ сущности должен называться `id`, а внешние ключи должны заканчиваться на `_id`.
- Типы данных должны соответствовать значениям.
- Повторяющиеся значения должны быть ограничены с помощью `UNIQUE` или составного ключа.
- Обязательные значения должны быть отмечены как `NOT NULL`.
- Схема должна соответствовать 3НФ.
- В схеме не должно быть отдельного хранилища общего количества просмотров, если оно вычисляется из событий просмотра.
- Пароль должен храниться в виде результата безопасного хеширования, а не как обычный текст.

## Что нужно сдать

1. Список самостоятельно выделенных сущностей.
2. Описание всех таблиц и полей.
3. Первичные, внешние и уникальные ключи.
4. Отдельный список всех связей между таблицами.
5. Типы и обязательность полей.
6. Краткое обоснование связей M:N.
7. Объяснение, какие показатели будут вычисляться из сохранённых данных.

Таблицы, поля и связи в задании намеренно не перечислены. Их определение является основной частью проектирования.
